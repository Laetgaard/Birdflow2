# Task #68 — Preview, approve, customise and pay after onboarding

## Primary objective

Rebuild the end of BirdFlow onboarding so customers can:

1. See the actual generated multi-page website.
2. Inspect and download their complete brand guide.
3. Approve the result and choose between:

   * Immediate Stripe card payment.
   * A Stripe invoice due on the first day of the following calendar month.
4. Request a free 30-minute website improvement meeting instead of paying.
5. Return later to the exact same state without restarting onboarding.

The existing onboarding interview and core website generation pipeline must continue working.

The existing website booking system and API are already functional. Reuse its architecture and APIs for BirdFlow’s internal onboarding meetings. Do not build a second unrelated booking engine.

---

* How the builder canvas renders pages.

* How the existing Brand tab reads and writes brand-guide data.

* Existing Stripe customer, Checkout, subscription and webhook logic.
* Existing admin authentication and role checks.
* Existing email service and production-only email guards.
* Existing origin/base-URL utilities.

Do not duplicate existing utilities, renderers, booking logic, Stripe customers, brand-guide formats or origin-resolution functions.

Produce a brief implementation map internally, then implement the task in the phases below.

# Architectural requirement: use separate state dimensions

Do not represent the complete flow with one ambiguous onboarding status.

Use separate fields or equivalent existing fields for:

```ts
type GenerationStatus =
  | "not_started"
  | "generating"
  | "complete"
  | "failed";

type DecisionStatus =
  | "awaiting_decision"
  | "customisation_requested"
  | "meeting_booked"
  | "in_customisation"
  | "ready_for_review"
  | "approved";

type PaymentMethodChoice =
  | "card"
  | "invoice"
  | null;

type PaymentStatus =
  | "not_started"
  | "checkout_pending"
  | "invoice_open"
  | "paid"
  | "payment_failed"
  | "past_due"
  | "cancelled";
```

Also persist, where appropriate:

```ts
siteRevision: number;
reviewRevision: number | null;
approvedRevision: number | null;

meetingBookingId: string | null;

stripeCustomerId: string | null;

decisionUpdatedAt: Date;
```

Use the existing onboarding session or website record when that is architecturally clean. Otherwise create a one-to-one onboarding decision record.

Do not introduce duplicate sources of truth.

The customer must approve a specific website revision. If the website changes after approval but before payment, invalidate the old approval and require approval of the new revision.

# Phase 6 — Stripe card payment

## Price configuration

Use Stripe Price IDs as the source of truth.

The setup fee must be a one-time Stripe Price.

The subscription must be a recurring Stripe Price.

Do not hardcode amounts in:

```txt
client
server
shared/subscriptionPlans.ts
```

`shared/subscriptionPlans.ts` may identify plan keys or server-resolved price references, but frontend-visible amounts must come from a server endpoint that retrieves or safely caches Stripe Price information.

Suggested response:

```ts
{
  currency: "dkk",
  setupFee: {
    priceId: string;
    name: string;
    unitAmount: number;
  },
  subscription: {
    priceId: string;
    name: string;
    unitAmount: number;
    interval: "month";
  }
}
```

## Checkout session

Create one Stripe Checkout Session in subscription mode with:

```ts
line_items: [
  {
    price: recurringSubscriptionPriceId,
    quantity: 1
  },
  {
    price: oneTimeSetupPriceId,
    quantity: 1
  }
]
```

Include metadata that safely maps back to:

```ts
userId;
websiteId;
onboardingSessionId;
siteRevision;
decisionPath: "direct_approval";
paymentMethodChoice: "card";
```

Reuse the existing Stripe customer when one exists.

Generate success and cancel URLs using the application’s existing origin resolver.

Example destinations:

```txt
success:
  /onboarding?payment=success

cancel:
  /onboarding?payment=cancelled
```

Both URLs must resume the same onboarding decision record.

A cancelled Checkout must not restart onboarding or remove the approved website.

## Idempotency

Repeated clicks must not create multiple active subscriptions or repeated setup charges.

Use:

* A database transaction or payment-attempt record.
* Stripe idempotency keys.
* Existing open Checkout Session reuse where safe.
* Server-side checks for existing paid or pending billing records.

A useful idempotency scope is:

```txt
websiteId + siteRevision + paymentMethodChoice
```

# Phase 7 — Stripe invoice payment

When the customer chooses `Modtag faktura`:

1. Verify ownership.
2. Verify that the selected site revision is still current.
3. Find or create the Stripe customer.
4. Calculate the number of calendar days until the first day of the next month.
5. Create a Stripe subscription using the recurring Price.
6. Set collection method to `send_invoice`.
7. Add the one-time setup Price to the first invoice.
8. Store the subscription and invoice IDs.
9. Set BirdFlow payment status to `invoice_open`.
10. Show the hosted invoice URL where available.
11. Send the invoice through Stripe.
12. Prevent duplicate invoices.

Use the Stripe equivalent of:

```ts
stripe.subscriptions.create({
  customer: stripeCustomerId,
  items: [
    {
      price: recurringSubscriptionPriceId
    }
  ],
  collection_method: "send_invoice",
  days_until_due: daysUntilFirstOfNextMonth,
  add_invoice_items: [
    {
      price: oneTimeSetupPriceId
    }
  ],
  metadata: {
    userId,
    websiteId,
    onboardingSessionId,
    siteRevision: String(siteRevision),
    paymentMethodChoice: "invoice"
  }
});
```

Confirm the exact parameter format against the installed Stripe SDK version.

After the initial invoice is created, recurring invoice terms may use the existing BirdFlow/Stripe invoice configuration rather than permanently inheriting an unusual one-day or thirty-day first-invoice deadline.

## Invoice state

Show:

> Din faktura er sendt
> Betalingsfrist: 1. september 2026
>
> Vi giver dig besked, så snart betalingen er registreret.

Provide:

```txt
Se faktura
```

where Stripe provides a hosted invoice URL.

Do not display the customer as paid until the verified `invoice.paid` webhook has been processed.

Paid-only publishing or subscription features must remain gated while the invoice is open, unless the existing BirdFlow business rules explicitly allow access before payment.

The preview, brand guide and payment status screen must remain accessible.

# Phase 8 — Webhooks and billing state

Extend the existing webhook implementation rather than creating a second webhook endpoint.

Verify Stripe signatures using the raw request body.

Handle at minimum:

```txt
checkout.session.completed
invoice.paid
invoice.payment_failed
customer.subscription.updated
customer.subscription.deleted
```

Also handle asynchronous Checkout events if the existing enabled payment methods require them.

Webhook processing must be idempotent.

Store processed Stripe event IDs or use the project’s existing webhook deduplication system.

## Required behaviour

### checkout.session.completed

* Find the onboarding decision from metadata.
* Save Stripe customer and subscription IDs.
* Do not blindly trust URL query parameters.
* Update Checkout state.

### invoice.paid

* Find the related website/onboarding record.
* Confirm the invoice belongs to the expected Stripe customer and subscription.
* Set `paymentStatus = paid`.
* Set `paidAt`.
* Activate the paid BirdFlow subscription state.
* Ensure the setup fee is not processed twice.

### invoice.payment_failed

* Set the relevant failed or past-due state.
* Show a clear payment recovery action.
* Do not delete the customer’s generated site or brand guide.

### subscription.deleted

* Update the local subscription state using existing cancellation rules.
* Do not change historical onboarding approval records.

# Phase 10 — Resume logic

Create one server-derived resume decision.

The frontend must not guess the correct onboarding stage from local storage alone.

Suggested logic:

```ts
if (generationStatus !== "complete") {
  resume generation/interview state;
}

if (decisionStatus === "awaiting_decision") {
  show preview and initial decision screen;
}

if (
  decisionStatus === "customisation_requested" ||
  decisionStatus === "meeting_booked" ||
  decisionStatus === "in_customisation"
) {
  show customisation progress state;
}

if (decisionStatus === "ready_for_review") {
  show updated preview and approval screen;
}

if (
  decisionStatus === "approved" &&
  paymentStatus === "checkout_pending"
) {
  show approved result and payment retry option;
}

if (
  decisionStatus === "approved" &&
  paymentStatus === "invoice_open"
) {
  show invoice state;
}

if (paymentStatus === "paid") {
  show onboarding completion state and dashboard action;
}
```

Leaving during any state must preserve:

* Generated website.
* Pages and components.
* Brand guide.
* Selected decision path.
* Meeting booking.
* Approval revision.
* Payment attempt.
* Stripe references.

After a cancelled Stripe Checkout, return to the approved decision screen with the option to restart payment.

Do not restart the interview after generation is complete unless an authorised reset action is deliberately used.

# Security requirements

Every server endpoint that reads or modifies:

* A generated website.
* Onboarding answers.
* Brand-guide data.
* Booking data.
* Decision state.
* Stripe payment state.
* PDF downloads.

must verify ownership or admin authorisation.

Customer access must use a condition equivalent to:

```ts
website.ownerUserId === authenticatedUser.id
```

Admin access must use a verified server-side admin role.

Never trust these values from the client:

```txt
userId
website owner
setup fee amount
subscription amount
Stripe customer ID
payment status
admin role
site revision
```

Stripe webhook metadata is a mapping aid, not a replacement for validating the corresponding database record.

Do not expose secret keys, private onboarding answers or another customer’s preview through iframe routes, download endpoints or predictable IDs.
