#226 — Retained Onboarding QA Runs v2
Goal

Create fresh, repeatable end-to-end QA runs for Birdflow’s two onboarding paths:

Build website from scratch
Import an existing website

The purpose is not only to prove that onboarding technically completes. The test must verify that Birdflow produces a reviewable practitioner website draft with a correctly configured Birdflow-native booking experience.

Every result, including failed and blocked runs, must be retained for later inspection and comparison.

Core test question

For each onboarding path:

Can a completely new practitioner complete onboarding and receive a usable website draft where the expected content is present, the booking system is correctly configured, and the draft can be opened and reviewed through Birdflow?

A run must not pass merely because generation completed.

Test fixtures

Use fixed, repeatable practitioner data so future QA runs can be compared against each other.

Fixture B — Existing website import

Use a stable test website created specifically for QA.

The test website should deliberately contain known content such as:

Practitioner name
About section
Two services
Prices
Contact information
Images
Multiple pages/sections
Existing external booking CTA/link
Some information that Birdflow needs but the website does not contain

Example missing information:

Exact appointment duration
Booking availability
Online vs physical appointments
Cancellation rules

This lets QA verify that Birdflow distinguishes between:

Information it can import
Information it must ask the practitioner for
Information it must never invent
Critical import booking requirement

If the existing website contains an external booking provider, for example:

EasyPractice
Calendly
SimplyBook
Other external booking links/widgets

Birdflow should preserve the intent to book, but replace the external booking implementation with Birdflow’s native booking system.

QA should explicitly verify:

sourceHasBookingIntent = true
externalBookingCopiedIntoDraft = false
birdflowBookingAdded = true

The imported site must not accidentally keep users routed to the old booking provider unless that behavior is intentionally supported.

AI quality review

After the deterministic checks, run the existing AI quality analysis.

AI evaluation should judge things that cannot easily be determined programmatically.

Suggested categories:

Content quality
Does the website make sense for the practitioner?
Is the copy coherent?
Is information repeated unnecessarily?
Is there fabricated information?
Does the site feel complete?
Structure
Does the page hierarchy make sense?
Is important information easy to find?
Is booking prominent enough?
Is contact information accessible?
Design
Does it look professionally usable?
Is visual hierarchy clear?
Does mobile layout make sense?
Are images appropriate?
Conversion
Can a visitor understand:
who the practitioner is?
what they offer?
where they operate?
what it costs?
how to book?

Important architecture requirement

The QA runner must exercise the same core flow used by real users.

Avoid building a QA-only shortcut such as:

QA script
↓
insert DB records manually
↓
call generator directly
↓
pass

Prefer:

QA runner
↓
real onboarding orchestration
↓
normal onboarding APIs/services
↓
website generation
↓
booking setup
↓
builder state
↓
preview

The runner can automate the experience, but it should not bypass meaningful production behavior.

Direct database access is acceptable for:

retrieving IDs
recording QA evidence
assertions
cleanup utilities

But not as a replacement for the onboarding flow being tested.

Retention rules

Every QA execution creates completely fresh:

User
Onboarding session
Website
Builder state
Booking/service data

Existing QA fixtures must never be:

reused
overwritten
deleted
mutated to make the new test pass

All old retained runs remain inspectable.

Failure behavior

If any step fails:

Stop the run at the appropriate stage.
Preserve everything created so far.
Record the exact failure.
Store logs/error context.
Add available review links.
Add screenshots if a preview was reached.
Mark the run with the correct terminal status.

Never clean up a failed run automatically.

Admin verification

For both QA users verify:

Users

Admin → Users can locate the QA user.

Websites

Admin → Websites can locate the generated website.

Onboarding

The retained onboarding session points to the correct user and website.

Builder

The builder opens the same retained website.

Preview

The onboarding preview represents the same current draft.

Booking

Booking configuration displayed in admin/database belongs to the same retained practitioner and website.

Execution flow

Update the persistent QA system so it supports:

Phase 2 — Scratch onboarding

Create fresh QA user.

Run normal scratch onboarding.

Provide the predefined answers.

Generate draft.

Wait for generation completion.

Run objective checks.

Verify booking.

Capture screenshots.

Run AI quality evaluation.

Retain result.

Phase 3 — Import onboarding

Create separate fresh QA user.

Submit known QA source website.

Run normal import pipeline.

Capture import findings.

Provide missing information when onboarding requests it.

Generate draft.

Run objective checks.

Verify external booking conversion.

Verify native Birdflow booking.

Capture screenshots.

Run AI quality evaluation.

Retain result.

Out of scope

Do not fix defects discovered during the test.

Do not:

redesign onboarding
change builder UX
change admin UX
publish the QA sites
approve subscriptions
run payment
delete previous QA fixtures
modify generated websites manually to make them pass

The purpose of #226 is to expose the current product truth.

Important rule for Replit

Do not change product behavior simply to make QA pass.

If the generated website does not contain booking, record:

FAILED_BOOKING

If import misses important content, record it.

If mobile looks bad, record it.

If the generator invents a price, record it.

That is much more valuable to us than a green test.
