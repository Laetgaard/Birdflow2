Det jeg ville ændre
1. Introducer rigtig schemaVersion

Det største hul i planen.

Birdflow bør ikke forsøge at “gætte” sig til gamle formater for evigt.

På website-state:

{
  schemaVersion: 7,
  pages: [...],
  globalComponents: {...},
  navigation: {...},
  ...
}

Og så eksplicitte migrations:

v1 → v2
v2 → v3
v3 → v4
...
v6 → v7

Ikke:

if (site.header && !site.sharedHeader) ...
if (component.type === "oldHero") ...

spredt rundt i publisheren.

Det bliver ellers teknisk gæld meget hurtigt.

Min anbefalede #190-plan
Goal

Make every Birdflow website that contains valid historical customer content publishable through the current canonical generated-site pipeline, regardless of which previous builder/publisher version originally created it.

Publishing must remain transactional:

CURRENT LIVE WEBSITE REMAINS UNCHANGED
1. Add explicit site-state versioning
Add

Preferably in:

shared/siteStructure.ts
server/publisher/migrations/

Introduce something along these lines:

CURRENT_SITE_SCHEMA_VERSION = X

Every current site state should identify its schema version.

For historical records without one:

detectHistoricalSchemaVersion(state)

should determine which known historical shape it belongs to.

Then:

migrateSiteStateToCurrent({
  state,
  detectedVersion,
  targetVersion: CURRENT_SITE_SCHEMA_VERSION
})
Important

Migration needs to be:

deterministic
idempotent
lossless
side-effect free
independent of React/browser state

Meaning:

migrate(migrate(oldSite))

should effectively produce the same canonical state as:

migrate(oldSite)
2. Keep compatibility migration separate from normalization

I would specifically not dump everything into normalize.ts.

Have three concepts:

migration
↓
normalization
↓
validation
Migration

Understands old Birdflow formats.

Example:

hero_v1 → hero
siteHeader → shared.header
old navigation structure → current navigation structure
old image prop → current asset reference
Normalization

Makes already-compatible data consistent.

Example:

missing optional padding → default
undefined alignment → "left"
missing responsive config → backwards-compatible default
Validation

Determines whether publishing is safe.

Example:

page references missing component
asset cannot be resolved
navigation links to deleted page
unknown component type
corrupted custom component

Those responsibilities should not be mixed.

3. Historical components need an alias registry

This is important for Birdflow because you've changed components during development.

Instead of conditions spread around the generator:

if (type === "oldHero")
if (type === "hero-section")
if (type === "HeroComponent")

have something like:

historicalComponentAliases = {
  "hero-section": "hero",
  "HeroComponent": "hero",
  "old-contact": "contact",
}

But aliases alone are insufficient if the props changed.

Therefore:

componentMigrations = {
  oldHero: migrateOldHero,
  oldBooking: migrateOldBooking,
}

This lets Birdflow distinguish:

renamed component

from:

structurally changed component
4. Create an immutable publish snapshot

This is probably the most important publishing safeguard.

When the user presses Publish, create:

PublishSnapshot

containing the exact canonical state that will be deployed.

For example:

{
  jobId,
  siteId,
  sourceRevision,
  sourceSchemaVersion,
  targetSchemaVersion,
  pages,
  sharedComponents,
  navigation,
  assets,
  brandGuide,
  customComponents,
  settings
}

The worker should publish that snapshot, not continuously reread mutable project data.

Otherwise:

user clicks publish
migration starts
user edits website
worker reads newer state
deployment represents a mixture of states

That's exactly the kind of intermittent publishing bug that becomes horrible later.

5. Never silently delete unsupported content

This should explicitly become a Done criterion.

If an old project contains:

component type Birdflow no longer understands

Birdflow must not do:

unknown component → skip

That could turn:

7-section homepage

into:

4-section homepage

while still reporting a successful publish.

Instead:

PUBLISH_BLOCKED_UNSUPPORTED_COMPONENT

with information such as:

“The page ‘Forside’ contains an older FAQ component that cannot yet be safely converted. Your existing website remains live.”

And preferably internally:

{
  code: "UNSUPPORTED_HISTORICAL_COMPONENT",
  pageId,
  componentId,
  componentType,
  detectedSchemaVersion
}

{

  report: {

Example:

{

This will save you a ridiculous amount of debugging time later.

8. Collaborator publishing needs site access, not owner equality

The plan correctly identifies this, but I'd tighten it.

Avoid checks like:

site.userId === req.user.id

Publishing should call the same centralized permission function used elsewhere:

requireSitePermission({
  siteId,
  userId,
  permission: "publish"
})

Ideally distinguish:

view
edit
publish
manage
owner

Even if currently edit === publish.

Don't hardcode “collaborator means everything owner can do.”

Job polling

This is also important.

Don't authorize:

GET /publish-job/:id

only by job creator.

Authorize through:

job.siteId → site permissions

So:

Owner starts publish
Collaborator can see progress

and vice versa.

But:

unrelated user → 403
9. Vercel project recovery needs stronger identity rules

The current plan says:

Detect and validate compatible existing Vercel projects.

Correct, but define priority.

I would resolve deployment target roughly as:

1. stored Vercel project ID
2. stored team/account ID
3. verified existing project mapping
4. historical project-name lookup
5. create new project ONLY if definitively no project exists

The dangerous option is:

can't find old project → create another

That can lead to:

customer-site
customer-site-2
customer-site-abc123

and domains pointing at the wrong deployment.

Store IDs, not names

Your canonical record should ultimately contain:

vercelProjectId
vercelTeamId
projectName
productionAlias
customDomains[]

IDs should be authoritative.

Names are recovery hints.

10. Separate “deploy” from “activate”

This should be absolutely explicit.

Do:

build succeeds
↓
deployment succeeds
↓
deployment responds successfully
↓
aliases/domain confirmed
↓
commit publication state

Not:

update database to publishing URL
↓
try deployment

The current live state should remain:

publishedUrl
lastSuccessfulDeploymentId
publishedAt

until the new version is confirmed.

Then atomically replace them.

11. Don't let Vercel failure alter published state

Tests should specifically prove:

Starting state:

publishedUrl = "https://customer-domain.dk"
published = true
deploymentId = "old-good-deployment"

New deployment fails.

Expected:

publishedUrl === "https://customer-domain.dk"
published === true
deploymentId === "old-good-deployment"

Plus:

latestPublishJob.status === "failed"

Publishing status and current production state are two separate concepts.

One architectural rule I'd give Replit

The generator should eventually know nothing about legacy Birdflow formats.

That's the clean boundary:

LEGACY DATA
    ↓
migration layer
    ↓
CURRENT CANONICAL SITE
    ↓
publisher/generator

Not:

                    ↗ old format
generator handles → medium-old format
                    ↘ current format

That second architecture will become increasingly fragile every time you update Birdflow.

Revised Done Looks Like

I'd replace Replit's Done section with:

Any recognized historical Birdflow site state can be deterministically migrated into the current canonical schema without mutating the stored source state during publish.
Migration preserves all supported pages, components, text, links, media/assets, navigation, shared components, booking configuration and relevant site settings.
Unknown or unsafe legacy data blocks publishing before deployment rather than being dropped, guessed or replaced.
Publishing operates from an immutable canonical snapshot.
The generated-site validator and production build gate succeed before a Vercel deployment is allowed to affect production state.
Owners and authorized collaborators can start publishing and inspect publish-job progress using centralized site permissions; unrelated users receive no access.
Existing Vercel project/team/domain relationships are recovered and reused using stable IDs where available; uncertainty causes a preflight error rather than an automatic duplicate project.
A failed migration, validation, generation, build, deployment, verification or alias activation leaves the previous successful deployment, URL, domain and published status unchanged.
Publication metadata changes only after the new deployment has been successfully verified and activated.
Historical fixtures cover every known historical schema generation plus real sanitized legacy project shapes.
Automated tests prove migration idempotence, content preservation, renderer parity, collaborator access, existing-project reuse, duplicate prevention and production preservation on every failure stage.
