2. Drag-and-drop skal ikke direkte sende mails.

Formuleringen:

“successful moves update the booking atomically ... and trigger notification exactly once”

er teknisk lidt farlig.

Databaseændringen kan være atomisk. Mail/SMS/API-kald kan ikke være en del af samme database-transaktion.

Brug i stedet:

calendar interaction → validate → DB transaction → booking_updated event/outbox → notification worker

Så hvis noget retries, får kunden ikke tre mails om samme ændring.

3. Der mangler en ordentlig concurrency-model.

Dette er vigtigt:

already-claimed slots

Det er ikke nok at kontrollere det i frontend.

Hvis to personer forsøger at booke samme tid samtidigt, skal serveren være autoriteten.

Jeg ville eksplicit kræve:

BEGIN TRANSACTION

lock relevant practitioner/date availability
validate booking state
validate overlap
validate external busy periods
update booking
create audit entry
create notification outbox entry

COMMIT

Frontend-conflict detection er kun UX.

Serveren bestemmer altid.

Performance acceptance criteria

“remains responsive” bør erstattes med noget målbart.

Fx:

calendar fetch only visible range + buffer
500 bookings/month skal være problemfrit
100 visible events skal render uden mærkbar lag
navigation bør ikke refetche hele booking-historikken
realtime events dedupliceres via booking ID/version
optimistic mutation rollback <1 UI interaction
filters må ikke refetche data unødvendigt

Replit arbejder bedre, når “good” kan testes.

Én regel jeg ville skrive øverst i Replit-opgaven

Do not build new calendar UI on top of weak booking invariants. Server-side scheduling correctness, concurrency protection and idempotency take priority over visual features. The UI may optimistically preview a change, but only the server can authorize a booking mutation.

Og en anden:

External calendars are availability inputs and optional mirrors, never the authority for Birdflow bookings. Import the minimum external data necessary, and never expose customer or appointment-sensitive metadata to an external calendar by default.

Det vil sandsynligvis forhindre nogle af de værste arkitekturfejl.
