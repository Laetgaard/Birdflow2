#84 — Plan mode and Build mode for the Builder AI
Objective

Upgrade the existing Birdflow Builder AI into a two-mode assistant:

Build — the current fast editing experience for small, direct changes.
Plan — a read-only planning workflow for larger or structured requests, followed by controlled step-by-step execution of an approved plan.

The assistant must stay inside Birdflow’s existing data-only component architecture.

It must not generate or execute React, JavaScript, CSS files or other runtime code.

The new system must preserve all existing protections:

Rate limiting.
Mutation validation.
Large-change detection.
Destructive-change confirmation.
SVG sanitisation.
Image-generation limits.
Output validation.
Deterministic self-check.
Website ownership checks.
Product behaviour
Default mode

The assistant opens in:

Byg

Small requests continue working as they do today.

Examples:

Skift teksten på denne knap
Gør overskriften kortere

These should remain fast, direct Build-mode actions.

Large-request recommendation

Build remains the default, but use Birdflow’s existing server-side definition of a large change to recommend Plan mode.

The existing large-change heuristic in:

server/aiAgentTools.ts:85-134

currently includes:

Page deletion.
Brand-guide overwrite.
Preset overwrite.
Three or more removals.
More than 12 mutations.
Removal of more than 50% of a page.

Refactor this logic into one reusable function if it is not already reusable.

Do not create a second definition of “large”.

The same function must be used for:

Existing Build-mode large-change approval.
Recommending Plan mode.
Summarising destructive or large scope before plan approval.
Checking that actual plan execution remains inside approved scope.

When a direct Build-mode request produces a mutation proposal that meets this heuristic, do not execute it immediately.

Emit an SSE event showing:

Det her ligner en større ændring. Vil du lave en plan først?

Allow the user to:

Switch to Plan.
Continue through the existing Build-mode approval path.

Do not force Plan mode for users who deliberately choose the existing approval path.

Core architectural decisions
Separate plans from builds

A plan describes approved intent.

A build run records execution.

Do not store build progress only on the plan itself.

Required concepts:

AssistantPlan
AssistantPlanStep
AssistantBuildRun
AssistantBuildStepRun
Version plans

Every plan must have a monotonically increasing version.

Any customer action that changes the plan must invalidate approval:

Rename a step.
Edit a step description.
Reorder steps.
Add a step.
Delete a step.
Include or skip a step.
Change the selected page.
Add or change a comment that is intended to affect execution.
Regenerate machine-readable scope.

When this happens:

plan.version += 1;
plan.approvedVersion = null;
plan.approvedAt = null;
plan.destructiveApproval = null;

A build run must store the exact approved version it executes.

The server must never execute:

plan.version !== plan.approvedVersion
Plan history

Keep plan history per website.

Retain approximately the latest 20 plans.

Do not delete:

The active plan.
A plan referenced by an active build.
A plan whose snapshot is required for an undo action.

Older inactive history can be deleted or archived from the application service after a newer plan is persisted.

Do not rely on an interactive database command for this.

One active plan

Allow one active editable plan per website.

Previous plans remain available as history but cannot simultaneously act as the current draft.

One active build

Only one active or resumable build may exist for a website.

Enforce this at the database level.

Statuses considered active should include at minimum:

queued
running
pause_requested
paused

A partial unique PostgreSQL index should prevent concurrent active builds for the same website.

This is required because all steps mutate the same builder_state row.

Do not rely only on disabling the Build button in the UI.

Explicit SQL migration requirement

Database schema changes must be applied through explicit SQL migration statements.

The project forbids:

db:push

Do not run an interactive schema push.

At minimum, the migration needs to:

Add a monotonic revision to builder_state.
Create plan storage.
Create plan-step storage.
Create build-run storage.
Create build-step-run storage.
Add indexes and constraints.
Add the partial unique active-build constraint.

Adapt names and types to the project’s current ID conventions.

Conceptual SQL:

ALTER TABLE builder_state
ADD COLUMN revision integer NOT NULL DEFAULT 0;

Every builder-state write path must increment this revision.

Conceptual active-build constraint:

CREATE UNIQUE INDEX assistant_one_active_build_per_website
ON assistant_build_runs (website_id)
WHERE status IN (
  'queued',
  'running',
  'pause_requested',
  'paused'
);

Add an equivalent constraint for one active editable plan if the chosen table structure supports it cleanly.

Update shared/schema.ts to match the explicit SQL migration.

Builder-state revision control
Add a revision integer

builder_state currently has:

websiteId
state
createdAt
updatedAt

Add:

revision: number;

The revision must increase monotonically for every successful builder-state write.

Do not use updatedAt as a concurrency token.

Planning revision

When a plan is created:

plan.websiteRevisionAtPlanning = builderState.revision;
Approval check

Before approval, check whether the builder revision still matches the plan’s planning revision.

If not, revalidate all targets and mark the plan stale where necessary.

Build-start check

Before starting:

current builder revision === validated plan revision

Otherwise:

Mark the plan stale.
Explain that the website changed after the plan was prepared.
Offer to refresh the plan.
Do not execute.
Before every step

Before each step:

Read the current builder revision.
Compare it with the build run’s expectedRevision.
If it differs, pause.
Revalidate the plan step against the current state.
Never silently continue against changed content.
Atomic mutation application

Each build step must be applied atomically.

Recommended process:

Read state and revision.
Let the model propose the step mutations.
Validate all mutations.
Enforce approved scope.
Apply deterministic repairs.
Validate responsive behaviour.
Run sanitisation.
Prepare the final new builder state.
Save using a revision compare-and-swap.
Increment the revision exactly once.
Persist the completed step result.

Conceptual update:

UPDATE builder_state
SET
  state = $newState,
  revision = revision + 1,
  updated_at = now()
WHERE website_id = $websiteId
  AND revision = $expectedRevision
RETURNING revision;

If no row is returned:

Do not apply the step.
Mark it paused because the website changed.
Emit a stale-state event.
Client autosave

All existing builder-state save paths must increment the revision.

The client autosave must not silently overwrite newer AI changes with an older local state.

Where practical, send the client’s expected revision with autosave and reject stale writes.

On conflict:

Do not overwrite the server state.
Inform the builder client that newer changes exist.
Reload or use the project’s safest existing reconciliation behaviour.

This task must not leave AI execution protected while normal autosave can still overwrite it immediately afterwards.

Build execution
One server-side build orchestration

A multi-step build must run as one server-side build orchestration.

Do not treat every plan step as a new public agent request.

The existing user rate limit is:

10 agent runs per user per 10 minutes

A 12-step build must not consume 12 public rate-limit units.

Starting or resuming one approved build should count as one agent run according to the current route-level limiter.

Internal step execution must happen inside that run or through an internal executor that does not independently pass through the public request limiter for each step.

Existing image budget

Therefore:

A complete build may generate at most three unique new images.
Reusing existing images does not count.
Reusing the same generated image does not count as another unique image.
Sanitised SVG illustrations follow their existing tool rules.
The plan validator must identify when the requested plan exceeds the image limit.
Plan mode should consolidate imagery or clearly explain the limit before approval.

Do not silently reset the image budget for every step.

Pause, stop, skip and resume
Stop behaviour

“Stop” means stop between steps.

If the current step has already started:

Let its atomic execution complete or fail.
Do not start the next step.
Keep all completed changes.
Set the build to paused or stopped, depending on the selected action.

Do not cancel halfway through a database write.

Resume

Resume from the first incomplete included step.

Do not rerun completed steps.

Before resuming:

Check the current builder revision.
Revalidate remaining targets.
Pause as stale if the website changed.
Skip

A failed or pending step may be skipped.

Before skipping:

Check dependsOnStepIds.
Identify later steps that require it.
Mark dependent steps blocked.
Explain which later work cannot run.

Do not blindly continue into cascading invalid references.

Undo the entire build

Before execution starts, store the complete builder-state snapshot and revision.

After a completed, paused or stopped build, provide:

Fortryd hele bygningen
Safe undo

If the current builder revision still equals the build’s last known revision:

Restore the pre-build snapshot.
Increment the builder revision.
Mark the build undone.
Preserve the build history and summary.
Newer changes after build

If the builder revision has advanced because of later manual or AI changes:

Do not silently overwrite them.
Explain that undoing the build would also remove newer work.
Require explicit destructive confirmation.
Take a safety snapshot of the current state before restoring.
