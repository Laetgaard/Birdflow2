# Birdflow Generative Website Runtime — Lovable-level creative AI with Birdflow editability, reuse and reliable publishing

## Mission

Upgrade Birdflow from an AI-assisted component builder into a true generative website system where Kimi K3 can design highly customized, premium websites with substantially more creative freedom while Birdflow guarantees:

* editability
* responsive behavior
* reusable account components
* safe interactions
* brand awareness without creative imprisonment
* visual verification
* builder/publisher parity
* secure publishing
* undo/version safety

The target experience is closer to Lovable-level design flexibility, but without abandoning Birdflow's structured builder.

Kimi should control:

**design reasoning, architecture, creative direction and composition**

Birdflow should control:

**component contracts, security, editability, responsiveness, capabilities, persistence, preview and publishing**

Do NOT solve this by allowing arbitrary untrusted React/JS generation.

The existing safe component DSL should evolve into Birdflow's generative design runtime.

---

# Product decisions — treat these as locked

## Component reuse

Every genuinely new AI-created section should normally become a reusable component definition and be saved to the customer's **account-level component library**.

It must not remain trapped inside one website's `builder_state`.

---

## Master vs instance behavior

Placed components are independent instances by default.

Editing one instance changes that instance only.

The UI and AI should additionally support explicit operations equivalent to:

* Update master component
* Update all linked instances

Do not silently propagate instance edits.

---

## Cross-site reuse

When a component from Website A is inserted into Website B with another brand identity, Birdflow should offer:

* **Use original design**
* **Adapt to this website's brand**

Do not automatically destroy the original visual identity.

---

## Creative exploration

The brand guide is the default design context, NOT an absolute creative restriction.

Support three creative intents:

```ts
brand_aligned
brand_evolution
experimental
```

Kimi may proactively propose improvements outside the existing brand when there is a strong design reason.

Significant deviation requires user approval before replacing the active design.

For normal work, show one actual alternative preview when useful.

For onboarding/full redesign, support 2–3 directions such as:

* Brand Safe
* Brand Evolution
* Bold / Experimental

The user may combine ideas from several directions.

---

## Embedded product capabilities

Custom AI-designed sections must be able to contain trusted Birdflow functionality such as:

* booking
* contact form
* newsletter
* product grid
* product detail where appropriate

Kimi must NOT implement those capabilities by generating arbitrary backend or JavaScript code.

Birdflow provides trusted capability nodes and runtime implementations.

---

## Advanced design freedom

Expand the safe design DSL to support controlled versions of:

* relative positioning
* absolute positioning
* sticky positioning where appropriate
* inset/top/right/bottom/left
* z-index/layers
* transforms
* rotation
* scale
* overlap
* aspect ratio
* clip-path
* masks where safely supportable
* advanced responsive visibility
* decorative layers
* pseudo-element-like decoration through explicit nodes
* richer image placement
* responsive layout transformations

Everything must pass through typed allowlists and sanitization.

---

## Safe interaction system

Kimi should eventually be able to create interactions such as:

* accordion
* tabs
* carousel
* expandable cards
* interactive timeline
* modal
* disclosure
* before/after
* simple toggles

Do NOT allow arbitrary JavaScript.

Create a declarative behavior DSL interpreted by Birdflow.

---

## Node-level editing

Users and the AI must be able to work inside generated components:

```text
section
  → layout
     → card
        → heading
        → body
        → image
        → button
```

Nodes should be individually selectable and editable.

AI mutations should be able to update one node without replacing the entire custom tree.

---

## Standard vs custom components

Remove the design philosophy:

> Prefer standard components.

Replace it with:

> Use the representation that produces the strongest result while preserving editability and reliability.

Rules:

* If an existing standard/custom component is already excellent → reuse it.
* If it only needs modification → adapt it.
* If it limits the design → create a new component.
* Existing components are resources, not creative constraints.

---

## Autonomous site building

After the user approves the overall site/design plan, normal implementation should run autonomously:

```text
build
→ render
→ screenshot
→ visually review
→ fix
→ verify
→ continue
```

Do not require approval for ordinary design decisions.

Pause only for:

* destructive changes
* material brand deviation
* genuinely sensitive/global changes
* actions already covered by Birdflow's approval rules

---

## Version history

True multi-version website history is wanted, but it may be Phase 2.

Do not block the core generative-runtime work on this.

Preserve the existing build snapshot/undo behavior during migration.

# Architectural finding that must be solved first

Birdflow currently has two independent visual render paths:

### Builder

```text
ComponentRenderer.tsx
→ hardcoded React standard components

CustomComponentRenderer.tsx
→ recursive custom DSL renderer
```

### Publisher

```text
templates.ts
→ separate JSX/string generation implementations
→ separate custom renderer
→ separate responsive handling
→ separately embedded motion/runtime logic
```

This is the largest architectural blocker.

Every new visual feature currently risks requiring implementation twice.

Do NOT dramatically expand the generative DSL on top of this duplicated architecture first.

The first major milestone must be to establish a shared rendering/runtime contract that builder and published websites both consume.

# TASK #163 — Shared Rendering Runtime

## Objective

Eliminate the architectural drift between builder preview and published websites.

Establish one canonical rendering contract.

---

## Audit first

Before implementation identify:

* what parts of standard component rendering can genuinely be shared
* what code depends on editor-only callbacks
* what runtime dependencies published Next sites may use
* what logic can move out of `ComponentRenderer.tsx`
* what logic can move out of `templates.ts`
* how token resolution differs
* how responsive rendering differs
* how motion differs
* how custom component rendering differs
* how booking/forms require publisher-specific behavior

Do not blindly move the entire current builder renderer into `shared`.

---

## Target architecture

Aim toward something equivalent to:

```text
BuilderState
    │
    ▼
Shared component/render specification
    │
    ├── standard component definitions
    ├── custom primitive renderer
    ├── styles
    ├── responsive resolution
    ├── design tokens
    ├── motion
    └── trusted capabilities
              │
        ┌─────┴─────┐
        ▼           ▼
 Builder adapter   Publisher adapter
```

Editor-only functionality must remain in the builder adapter.

Backend/runtime-only functionality remains in publisher capability adapters.

Visual rendering rules should not be independently rewritten.

---

## Important rule

The source of truth should become:

```text
Component definition + shared visual runtime
```

not:

```text
Builder implementation
PLUS
Publisher imitation
```

---

## Migration strategy

Do this incrementally.

Start with custom components because their DSL is already structured.

Then migrate standard components in groups.

Do not perform a high-risk all-at-once rewrite.

---

## Shared runtime responsibilities

Centralize:

* style normalization
* design token resolution
* responsive resolution
* motion definitions
* custom primitive rendering contract
* shape/SVG resolution
* component visual schemas
* capability placeholders
* sanitization rules

Publisher generation may still copy runtime source into the standalone project if necessary.

The crucial requirement is that the source copied into publisher output originates from the same implementation/contracts used by preview.

---

## Fix known parallax mismatch during migration

The audit identified `parallax` as existing in schema vocabulary but missing from the active resolver.

Fix this and add contract tests so motion vocabulary cannot contain runtime-unimplemented effects.

---

## Tests

Expand parity tests.

Custom components must no longer be excluded merely because their renderers differ.

Add tests proving:

```text
same BuilderComponentData
→ same meaningful DOM/styles/content
```

for builder and publisher adapters.

Also test:

* responsive variants
* SVG assets
* tokens
* motion
* images
* nested custom trees

---

## Done when

A new visual primitive can normally be added to ONE shared visual contract and become available in:

* builder preview
* screenshots
* publisher output

without separately recreating its rendering semantics in `templates.ts`.

## Absolute positioning rules

Absolute positioning creates substantial responsive risk.

Require:

* positioned ancestor detection
* safe overflow handling
* responsive overrides
* mobile guard checks
* viewport screenshot verification for generated layouts

Kimi must not use absolute positioning for basic layouts that should use flex/grid.

It is intended for intentional compositions and decorative layering.

---

# Responsive component model

Generated components must have explicit responsive behavior.

Every AI-created section should support:

```text
desktop/base
tablet
mobile
```

Kimi should think about structure, not merely shrink values.

Allow transformations such as:

```text
2 columns → 1 column
horizontal → vertical
image left → image below
decorative layer visible → hidden
grid 4 → 2 → 1
overlap desktop → normal flow mobile
```

Use CSS ordering/visibility where possible instead of maintaining three unrelated component trees.

---

# Node-level AI mutation tools

Add dedicated tools such as:

```text
get_custom_component_tree
get_custom_node

add_custom_node
update_custom_node
update_custom_node_styles
update_custom_node_content
move_custom_node
duplicate_custom_node
remove_custom_node
```

Naming can differ according to existing conventions.

Do NOT require Kimi to replace the entire component tree just to change one nested element.

---

## Stable node addressing

Every node needs a stable ID.

Node mutations should include:

```text
pageId
componentId
nodeId
```

and use current website revision/CAS protection.

Return the changed node and resulting revision/state summary.

---

# Editability

Generated components should automatically produce a meaningful editable schema.

For example, Kimi creates:

```text
Hero
├── eyebrow
├── heading
├── description
├── image
└── CTA
```

Birdflow should expose those fields in the properties panel without requiring a manually coded standard-component registry entry.

Also support direct node selection for advanced editing.

---

## Property editing levels

Support:

### Simple customer controls

* text
* image
* link
* color slots
* commonly useful spacing
* alignment

### Advanced controls

When the user selects an individual node:

* layout
* typography
* spacing
* sizing
* border
* radius
* shadow
* responsive
* motion
* layering where applicable

Do not overwhelm normal users with every primitive property by default.

---

# Tree complexity

The existing 400-node hard cap can silently truncate complex AI trees.

Replace silent truncation behavior.

If the safe limit is exceeded:

* reject before save
* return a structured error
* tell Kimi how many nodes are allowed
* encourage component decomposition

Do not silently alter the generated design.

Consider allowing nested reusable subcomponents rather than simply increasing the cap dramatically.
